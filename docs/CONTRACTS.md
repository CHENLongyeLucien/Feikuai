# PaymentGuard implementation and operations

The supported transfer route is `executePayment` in `contracts/src/PaymentGuard.sol`. A six-decimal DEMO token is minted once; the guard has no owner, setter, withdrawal, rescue, allowance or upgrade entry point. Every successful transfer consumes one authorization nonce and permanently records one digest per invoice key. Cancellation consumes the nonce only when the immutable approver actually sends the contract transaction.

Compiler settings: Solidity 0.8.37, Cancun, optimizer 200 runs, via IR; Foundry 1.8.1. OpenZeppelin 5.7.0 is pinned through the workspace lockfile. The official [Solidity release](https://github.com/argotorg/solidity/releases/tag/v0.8.37) and [OpenZeppelin release](https://github.com/OpenZeppelin/openzeppelin-contracts/releases/tag/v5.7.0) were checked during implementation. OZ's short-domain-name requirement is compatible with the specified name. No protocol deviation was necessary.

Run `pnpm contracts:build`, `pnpm contracts:export-abi`, and `pnpm test:contracts`. The ABI is generated from actual compiler artifacts and exported from one chain package. `docs/contract-results.log` holds actual Foundry output. The stateful invariant handler repeatedly tries valid, invalid-signer, repeated-invoice, repeated-nonce and cancellation sequences. It checks exact balance conservation, a maximum of one success per invoice, and equivalence of consumed state with observed successful calls. The invariant deliberately operates on eight synthetic invoice keys; this is not an exhaustive proof or audit.

Local startup: `pnpm chain:local`, then `pnpm contracts:deploy:local`. Deployment uses Anvil's unlocked JSON-RPC accounts only after checking loopback and chain 31337. It stores a local transaction journal and verifies an existing manifest instead of creating another funded vault. Roles are local Anvil accounts 0 (funder/deployer), 1 (approver), 2 (relayer), 3–4 (suppliers). These are public development accounts; never fund or reuse them outside isolated local development. Invoice identity remains the responsibility of the trusted registry; deployment assigns no invoices.

`node --import tsx scripts/chain-local-test.ts --golden-only` compares viem and Solidity hashes on the deployed contract and saves a public cross-language fixture. Without the flag it additionally uses the isolated unlocked approver account for an automated 1 DEMO protocol transfer, verifies exact deltas/event, and sends two bounded actual negative transactions (unsigned request and replay). It writes `docs/local-chain-results.json`. This automated local wallet test is distinct from human wallet review. Do not run it while application integration uses the dedicated relayer account.

Fuji configuration uses public `FUJI_DEPLOYER_ADDRESS`, `FUJI_APPROVER_ADDRESS`, `FUJI_RELAYER_ADDRESS`, `FUJI_SUPPLIER_1_ADDRESS`, and `FUJI_SUPPLIER_2_ADDRESS`, plus `FUJI_RPC_URL` if overriding the official C-Chain endpoint. All five roles must differ and known Anvil addresses are rejected. Import an independently created deployer into encrypted Foundry keystore `sf-fuji-deployer`; the script never reads a deployer or approver private-key environment variable. Fund deployer for deployment gas, relayer for execution gas, and approver for cancellation gas with test AVAX. Typed-data signing alone requires no gas. Deployment mints 1,000,000 valueless DEMO and funds the vault with 300,000 DEMO.

`pnpm contracts:deploy:fuji` first checks the RPC reports chain 43113, then simulates through the named keystore. After reviewing the public roles and simulation, `pnpm contracts:deploy:fuji -- --broadcast` submits those synthetic deployments. Mainnet 43114 fails closed. If interrupted, inspect the Foundry broadcast journal; `--recover-manifest` reads already executed receipts, or `--resume --broadcast` resumes journaled transactions. The wrapper refuses to create another vault when a broadcast journal already exists. A manifest is emitted only from successful actual token/vault/funding receipts. The Fuji manifest and trusted registry must be pinned into a newly built approver.

`pnpm fuji:preflight` checks actual code hashes, policy derivation/getters, ordered supplier mappings, DEMO decimals/supply, vault liquidity, role separation and relayer/approver native balances. `pnpm test:fuji` records read checks. Add `-- --broadcast-negative` only for the documented intentional unsigned transaction: at most 150,000 gas and a default maximum fee-per-gas of 100 gwei, paid by the pinned relayer. The command never invents a positive Fuji settlement. Real approval/signing, application execution and evidence must separately verify a payment. Missing credentials, funds or manifest remain explicit blockers.

The deployer has no later treasury control. Loss of approver access can strand demonstration funds; the cap is per invoice payment, not a cumulative budget. Invoice duplication under deliberately different keys, offchain settlement elsewhere and compromised/malicious supported-token semantics are outside the guarantee. ERC-1271 approvals and mainnet operation are unsupported. Receipt files are observations, not standalone consensus proofs; independent verification needs a trusted RPC and deployment pin.
